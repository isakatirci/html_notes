Soru 1. Coordinator-Subagent Pattern'i tanımak

Senaryo: Customer Support Resolution Agent

Bir ekip, Claude Agent SDK ile müşteri destek sistemi kuruyor. Tasarım şöyle: tek bir primary agent tüm müşteri isteklerini alır, kategoriyi belirler (billing, returns, account), sonra her birinin kendi tool seti ve system prompt’u olan specialized agent’lara işi devreder. Primary agent sonuçları birleştirip müşteriye cevap verir. Bu tasarım hangi architectural pattern’i anlatır?

  1. Pipeline orchestration — sabit sıralı handoff
  2. Peer-to-peer multi-agent işbirliği
  3. Coordinator-subagent pattern — task delegation ile
  4. Tek agent, dinamik tool loading

Doğru cevap: C

Bu, klasik coordinator-subagent pattern’dir. Şöyle düşün: ofiste bir koordinatör (coordinator) vardır. Müşteri ona gelir. Koordinatör işin türünü anlar, fatura uzmanına veya iade uzmanına gönderir, sonra cevapları tek bir müşteri mesajında birleştirir.

Tek merkezî agent istekleri alır, görevlere böler, uzman subagent’lara delegate eder ve sonuçları synthesize eder. Coordinator workflow’u yönetir; subagent’lar domain-specific execution yapar. Üç işaret: bir merkezî agent, kategoriye göre branching delegation, cevap öncesi synthesis.

Bu yüzden doğru şık C’dir. Bir merkez var. Uzmanlar var. En sonda tek bir müşteri cevabı var.

İşin özü budur. Coordinator yolu çizer. Subagent işi yapar. Sonuçlar tekrar coordinator’da toplanır.

Neden diğer şıklar yanlış:

A) Pipeline sabit bir sıra demektir: A biter, B başlar, C başlar. Burada akış kategoriye göre dallanır. Billing isteği returns agent’ına gitmez. Linear pipeline değildir. Kategori değişince yol da değişir. Sabit boru hattı bu işi taşımaz.

B) Peer-to-peer’de agent’lar birbirine doğrudan konuşur, merkez yok. Burada net bir hub-and-spoke yapı var: her şey coordinator üzerinden geçer. Burada uzmanlar birbirine değil, merkeze bağlıdır.

D) Dinamik tool loading, her şeyi tek conversation / tek context içinde tutar. Burada ayrı agent’lar, ayrı prompt ve ayrı tool set var. Bu isolation tek agent değildir. Ayrı prompt ve ayrı tool set görüyorsan bu tek agent değildir.

CCA ipucu: Coordinator-subagent sınavda en çok çıkan multi-agent pattern’dir. Ezberle: bir coordinator, birden fazla specialized subagent, final response öncesi synthesis. Coordinator-subagent görünce üç şeyi say: merkez, uzmanlar, synthesis.

Soru 2. Agentic loop ve stop_reason

Bir architect, Claude Agent SDK uygulamasını debug ediyor. Agent kullanıcı sorgusunu alır, içinde bir tool call olan yanıt üretir. Uygulamanın sıradaki adımı seçmesi gerekir. API yanıtında stop_reason alanı vardır. stop_reason değerinin tool_use olması ne anlama gelir?

  1. Agent bir tool çağırmak istiyor ve devam etmeden önce tool result bekliyor
  2. Agent işi bitirdi ve tool başarıyla kullanıldı
  3. Tool execution başarısız oldu, agent retry istiyor
  4. Agent maksimum tool call limitini aştı

Doğru cevap: A

tool_use bir niyet sinyalidir, tamamlanma sinyali değildir. Model durmuştur çünkü bir tool çağırmak ister. Senin uygulamanın yapması gereken: tool’u çalıştır, sonucu geri ver, agentic loop devam etsin.

Döngü şudur: generate → stop_reason: tool_use → tool’u execute et → result’ı geri ver → tekrar generate → end_turn. Sık yapılan hata: “tool_use gördüm, demek ki tool bitti” sanmak. Hayır: tool henüz senin kodunda çalışmamıştır.

Yani model “ben bitirdim” demez. Model “bir tool’a ihtiyacım var” der ve bekler.

Sen tool’u çalıştırmazsan döngü orada kalır. Sonuç gelince model kaldığı yerden devam eder. Bitiş ancak end_turn ile gelir.

Neden diğer şıklar yanlış:

B) Tool henüz kullanılmamıştır. Bu, uygulamanın tool’u çağırması için bir request’tir. Bitiş end_turn ile gelir. tool_use henüz bir istektir.

C) tool_use normal invocation isteğidir. Tool hatası, sen execute ettikten sonra ortaya çıkar; stop_reason olarak gelmez. Hata, tool senin kodunda çalıştıktan sonra doğar.

D) Tool limiti aşımı için standart bir stop_reason yoktur. Limit application layer’da (senin kodunda) enforce edilir. Limit aşımı stop_reason olarak gelmez. Onu sen sayarsın.

CCA ipucu: stop_reason modelin bir sonraki adım niyetini söyler. tool_use = “ben durdum, sen tool çalıştır”. end_turn = “cevabım hazır”.

Soru 3. Subagent context isolation

Senaryo: Multi-Agent Research System

Coordinator agent, quantum computing üzerine uzun bir konuşma yapıyor. Sonra Agent tool ile bir research subagent’a şu görevi verir: quantum error correction üzerine güncel paper’ları bul. Research subagent hangi context’e erişir?

  1. Coordinator ile kullanıcı arasındaki tam conversation history
  2. SDK’nın otomatik ürettiği özetlenmiş conversation history
  3. Conversation history artı coordinator’ın system prompt’u
  4. Yalnızca Agent tool ile geçilen prompt string’i, plus subagent’ın kendi system prompt ve tool definition’ları

Doğru cevap: D

Subagent’lar fresh conversation ile başlar. Basit bir örnek: yeni bir stajyeri odaya çağırırsın. Önceki 40 dakikalık toplantıyı duymaz. Sadece senin kapıdan söylediğin cümleyi duyar.

Subagent’ın elinde olanlar: kendi system prompt (AgentDefinition), Agent tool ile geçilen prompt string, (varsa) project-level CLAUDE.md, kendi tool definition’ları.

Parent conversation history ve coordinator system prompt otomatik geçmez. Bu context isolation kasıtlıdır.

Bunu unutmak kolaydır. Coordinator uzun konuşmuştur. Subagent’ın da aynı şeyi bildiğini varsayarsın. Varsayma.

Gerekli bilgiyi prompt string’e sen yazarsın. File path, karar, hata mesajı. Yazmazsan subagent bunları göremez.

Neden diğer şıklar yanlış:

A) Subagent parent history’yi inherit etmez. Her subagent boş slate ile başlar. Bu kavram sınavda sık test edilir. Uzun parent konuşma subagent’a akmaz. Bunu varsayma.

B) SDK conversation’ı otomatik özetleyip subagent’a vermez. Özet istiyorsan coordinator’ın prompt string’ine sen yazarsın. Otomatik özet yoktur. Özet istiyorsan sen yazarsın.

C) Coordinator’ın system prompt’u subagent’a akmaz. Subagent kendi prompt’u ile çalışır. Coordinator’ın system prompt’u başka bir odanın kuralıdır.

CCA ipucu: Sınav tuzağı: ‘subagent context’i inherit eder’ varsayımı. Etmez. Tek kanal, Agent tool’a verdiğin prompt string’dir. Gerekli context’i (file path, karar, hata) açıkça yaz.

Soru 4. Task decomposition stratejisi

Müşteri iade (refund) işleyen bir agent kurulacak. Adımlar: (1) siparişin varlığını doğrula, (2) iade politikasını kontrol et, (3) tutarı hesapla, (4) payment system’de iadeyi başlat. En uygun decomposition hangisidir?

  1. Her adım için ayrı subagent, üstte bir parent coordinator
  2. Tek agent + dört tool — adımlar sequential ve context paylaşıyor
  3. İki subagent (validation+policy, calculation+payment)
  4. Batch API ile dört adımı aynı anda işle

Doğru cevap: B

Bu adımlar sequential’dir: 3. adım 1 ve 2’nin sonucuna ihtiyaç duyar. Ayrıca aynı sipariş / aynı müşteri context’ini paylaşırlar. Toplam tam dört tool — önerilen 4–5 tool bandının içinde.

Sequential + shared context işler tek agent + odaklı tool’larla çözülür. Subagent burada gereksiz handoff maliyeti ekler.

Basit kural: subagent, işler birbirinden bağımsız / parallel çalışabiliyorsa değer üretir. İade gibi ‘önce şunu, sonra bunu’ akışında tek agent daha doğru.

İade bir zincirdir. Sipariş yoksa politikaya bakılmaz. Politika reddediyorsa tutar hesaplanmaz.

Bu zinciri dört odaya bölmek işi yavaşlatır. Her oda bir öncekinin söylediğini yeniden öğrenmek zorunda kalır. Tek agent aynı siparişi unutmaz.

Neden diğer şıklar yanlış:

A) Dört subagent, dört kez context kaybı ve coordinator maliyeti demektir. Independent/parallel işler için uygundur, linear refund için değil. Dört oda, dört kez anlatım demektir. İade bunu istemez.

C) Hâlâ sequential işe handoff karmaşıklığı ekler. Paralel kazanç yok. İkiye bölmek de sırayı paralel yapmaz. Zincir zincirdir.

D) Batch API real-time olmayan, yüksek hacimli iş içindir (latency 24 saate kadar). Kullanıcı bekleyen iade için uygun değil. Müşteri iade ekranında 24 saat bekleyemez.

CCA ipucu: Her workflow subagent istemez. Bağımsız ve parallelizable iş için subagent; sequential + shared context için tek agent.

Soru 5. Silent subagent failure

Senaryo: Customer Support Resolution Agent

Coordinator, billing dispute’u billing subagent’a delegate eder. Subagent bir authentication error alır ama yalnızca şunu döner: “I was unable to complete the analysis.” Coordinator müşteriye der: “Your billing dispute has been reviewed and no action is needed.” Bu failure’ın root cause’u nedir?

  1. Subagent silent failure yaptı; coordinator failure’ı ayırt edecek context’e sahip değildi
  2. Coordinator system prompt’unda billing dispute talimatı yok
  3. Billing API timeout’u kısa
  4. Coordinator billing için Batch API kullanmalıydı

Doğru cevap: A

Bu, silent subagent failure anti-pattern’idir. Coordinator belirsiz bir cümle alır. “Dispute bulunamadı” ile “hiç arama yapılamadı” aynı görünür. Bu yüzden yanlış müşteri cevabı üretir.

Düzeltme: subagent structured status dönmeli (success / failure / partial) ve somut error detail eklemeli. Örnek: status=failure, error_type=authentication, retryable=false.

coordinator ‘zeki’ olsa bile, eline sinyal gelmezse doğru karar veremez. Sorun prompt yazarlığı değil, error reporting tasarımıdır.

Müşteri “incelendi, işlem yok” duyar. Gerçekte inceleme hiç yapılmamıştır. Kimlik doğrulanamamıştır.

Coordinator kötü niyetli değildir. Elindeki cümle yetersizdir. Belirsiz cümle, yanlış karara dönüşür.

Neden diğer şıklar yanlış:

B) Mükemmel prompt bile eksik error sinyalini telafi etmez. Coordinator’ın göreceği tek şey subagent’ın son mesajıdır. Prompt, gelmeyen sinyali yaratamaz.

C) Timeout olsa bile asıl bug, hatanın coordinator’a structured olarak iletilmemesidir. Timeout ikincil olabilir. Timeout olsa bile asıl eksik, structured error’dır.

D) Batch API bu senaryoyla ilgisizdir. Real-time support + silent failure, batch ile çözülmez. Batch, sessiz hatayı konuşkan yapmaz.

CCA ipucu: Sınav tuzağı: silent failure’ı ‘prompt problemi’ gibi sunmak. Asıl tasarım hatası subagent error reporting’dir. Coordinator-side prompt engineering bunu tam kapatmaz. Prompt’u parlatmak, gelmeyen error’u doğurmaz.

Soru 6. tool_choice konfigürasyonu

Architect beş tool’lu bir agent kuruyor. Çoğu etkileşimde model tool’u serbest seçsin. Ama bir workflow’da her zaman önce validate_input çağrılsın. tool_choice nasıl ayarlanmalı?

  1. Genel için none, validation için any
  2. Genel için any, validation için auto
  3. İkisinde de required, asıl işi system prompt’a bırak
  4. Genel için auto; zorunlu validation için {"type": "tool", "name": "validate_input"}

Doğru cevap: D

auto = model karar verir (konuşma da olabilir, tool da). İsimli form {{"type": "tool", "name": "X"}} = o tool mutlaka çağrılır.

Kritik kurallar için programmatic enforcement, prompt tavsiyesinden her zaman daha güvenilirdir. “Lütfen önce validate_input çağır” demek probabilistic’tir. Named-tool form deterministic’tir.

İki ayarı karıştırma. Günlük sohbet için auto yeter. Zorunlu ilk adım için named-tool kullan.

“Lütfen önce şunu çağır” demek ricadır. Named-tool bir kilit gibidir. Kilit açılmadan sonraki oda görünmez.

Neden diğer şıklar yanlış:

A) none tool’ları tamamen kapatır. Genel etkileşimde tool gerekebilir. any ise belirli tool’u değil, ‘herhangi bir tool’u’ zorlar. none tool’u kapatır. any ise ‘şu tool’ demez.

B) any bazı tool çağrısını zorunlu kılar ama hangisini seçtiğini garanti etmez. Validation workflow’da tam tersi gerekir: belirli tool. Genel yolda any selamlaşmada bile tool zorlar. Genel yolda any, ‘merhaba’ya bile tool bağlar.

C) required ≈ any: bir tool çağrılmalı, hangisi modelin elinde. System prompt bunu deterministic yapmaz. Prompt, required’ı belirli bir tool yapmaz.

CCA ipucu: auto = model karar verir. any/required = bir tool zorunlu (model seçer). Named-tool = tam o tool. none = tool yok. Belirli tool için tek deterministic seçenek named-tool form’dur.

Soru 7. Parallel exploration için context forking

Senaryo: Multi-Agent Research System

Research coordinator’ın market trend üzerine 15 turn’lük konuşması var. Kullanıcı sorar: “Ya zıt market koşullarını varsaysaydık?” Ekip, mevcut thread’i kaybetmeden bu alternatifi keşfetmek istiyor. Claude Agent SDK ile doğru yaklaşım hangisi?

  1. Boş history’li yeni session aç, orijinal konuşmayı özetle
  2. Message history array’ini yeni API call’a elle kopyala
  3. ClaudeAgentOptions içinde fork_session=True ile mevcut session’ın branched kopyasını oluştur
  4. Agent tool parametresi olarak context: fork kullan

Doğru cevap: C

fork_session=True (Python) / forkSession: true (TypeScript), ClaudeAgentOptions içinde yeni bir session açar. Bu session, orijinal history’nin tam kopyasını alır ve bağımsız sapar. Orijinal session değişmez.

Fork, ‘what-if’ analizi için lossy özet yerine exact history kopyası verir. Git’teki branch gibi düşün. Ana dal durur, yeni dal aynı commit history ile açılır.

Kullanıcı “ya tersini varsaysaydık?” diye sorar. Eski konuşmayı silmek istemezsin. Özetlemek de istemezsin. Çünkü özet sayıları ve itirazları kaybeder.

Fork tam kopya açar. Ana dal yerinde durur. Yeni dal kendi yoluna gider. İki analiz birbirine karışmaz.

Neden diğer şıklar yanlış:

A) Özet lossy’dir. 15 turn içindeki nüans, sayı ve karşı argüman kaybolur. Parallel exploration tam history ister. 15 turn’lük nüans özetle ölür.

B) Elle kopya kırılgandır: eksik mesaj, yanlış rol, SDK session garantilerinin bypass’ı. Elle kopya bir mesajı bile düşürebilir.

D) context: fork geçerli bir Agent tool parametresi değildir. Fork, session option’dır. Böyle bir Agent tool parametresi yoktur.

CCA ipucu: Parallel exploration için fork_session=True + resume. Exact history korunur, dallar birbirini kirletmez.

Soru 8. Multi-agent research sistemi tasarlamak

Senaryo: Multi-Agent Research System

Bir konu üç bağımsız boyutta araştırılacak: academic papers, industry reports, news coverage. Her boyut farklı tool ister. Sonuçlar tek raporda synthesize edilecek. En uygun mimari?

  1. Coordinator + üç specialized subagent (boyut başına, her biri 3 tool), bağımsız çalışıp sonra synthesis
  2. Dokuz tool’lu tek agent, boyutları sequential işler
  3. Üç bağımsız agent shared database’e yazar, dördüncü agent raporu okur
  4. Sequential pipeline: her agent bulgularını bir sonrakine devreder

Doğru cevap: A

Bu, coordinator-subagent için ideal vakadır. Üç boyut bağımsızdır, parallel çalışabilir, tool set’leri farklıdır. Her subagent 3 tool ile 4–5 tool limitinin altında kalır. Coordinator decomposition + synthesis yapar.

Bağımsız araştırma kolları sequential pipeline’a zorlanmamalı; parallel subagent hem hız hem isolation verir.

Academic, industry ve news birbirini beklemek zorunda değildir. Üçü aynı anda yürüyebilir.

Coordinator en sonda birleşir. Her uzman kendi üç tool’u ile kalır. Dokuz tool’u tek kişiye yığmazsın.

Neden diğer şıklar yanlış:

B) Dokuz tool tool overload örneğidir. Model yanlış tool seçme ihtimalini yükseltir. Dokuz tool, yanlış kapıyı seçmeyi kolaylaştırır.

C) Shared database gereksiz altyapı karmaşıklığı ekler. SDK’nın doğal birimi conversation + dönen mesajdır. Ortak database bu senaryoda zorunlu değildir.

D) Pipeline, bağımsız işlere yapay sıra dayatır. News, academic’i beklemek zorunda değildir. Haber kolu paper kolunu beklemek zorunda değildir.

CCA ipucu: Sınav tuzağı: pipeline ‘daha düzenli’ görünür ama bağımsız işlerde performansı düşürür. Hız ve esneklik için coordinator + parallel subagent.

Soru 9. Escalation tasarımı

Customer support agent, nadir bir edge case’te üç kez çözüm denedi, başaramadı. Agent kendisi “%85 confident, issue resolved” diyor. Sistem sırada ne yapmalı?

  1. %85 confidence’e güven, ticket’ı kapat
  2. Prompt’a ek talimat koyup dördüncü kez dene
  3. İnsan agent’a escalate et; tam interaction history ve denenmiş tool’ları ver
  4. Daha büyük context window’lu modele geç

Doğru cevap: C

2–3 başarısız denemeden sonra insan’a escalate et ve tam context ver. LLM’nin söylediği confidence skoru kötü calibrated’dir — özellikle gerekli tool yoksa.

“%85 emin” bir termometre değil, modelin kendi cümlesidir. Tool’u olmayan bir agent yüksek confidence ile uydurabilir. Bu yüzden bounded retry with escalation kullanılır.

Üç deneme bitti. Aynı tool’lar duruyor. Dördüncü deneme yeni bir kapı açmaz.

İnsana ticket’ı at. Konuşmanın tamamını ver. Hangi tool’un denendiğini ver. İnsan oradan devam edebilsin. Boş bir “çözülemedi” notu yetmez.

Neden diğer şıklar yanlış:

A) Self-reported confidence tuzağı. Tool eksikken güvenilmez. Ticket kapatmak müşteriye yanlış ‘çözüldü’ der. Yüksek sayı, eksik tool’u gizler. Ticket kapanmasın.

B) Aynı tool set ile dördüncü deneme yeni yetenek üretmez. Sınır zaten 2–3’tür. Aynı aletle dördüncü vuruş yeni alet üretmez.

D) Daha büyük context window eksik tool yeteneği yaratmaz. Problem hafıza değil, capability + karar kapısıdır. Daha geniş pencere, olmayan tool’u yaratmaz.

CCA ipucu: Bounded retry (2–3) sonra escalate. Self-reported confidence tek başına karar kriteri olmasın.

Soru 10. Agent bölmek mi, tool eklemek mi?

Senaryo: Multi-Agent Research System

Research agent’ın şu an 4 tool’u var. Ekip patent search, regulatory lookup, financial data ve social media monitoring eklemek istiyor. En iyi yaklaşım?

  1. Dört yeni tool ekle (toplam 8)
  2. Dört tool ekle, description’ları iyileştir
  3. İki yeni specialized subagent oluştur (patent/regulatory ve financial/social, her biri 2 tool); orijinal agent’ı 4 tool ile coordinator yap
  4. 8 tool’lu tek agent + few-shot örnekler

Doğru cevap: C

Sekiz tool, 4–5 tool önerisini aşar. Yeni domain’leri specialized subagent’lara dağıt. Eski agent coordinator kalır, çekirdek tool’larını tutar, yeni işi delegate eder.

Tool sayısı şişince description cilası yetmez; karar uzayı büyür ve misrouting artar.

Dört tool’a dört yeni yetenek eklemek cazip gelir. Toplam sekiz olur. Sekiz, önerilen bandın dışındadır.

Yeni işleri yeni uzmanlara ver. Eski agent coordinator olsun. Kendi dört tool’unu tutsun. Geri kalanı delegate etsin.

Neden diğer şıklar yanlış:

Soru 60. End-to-end reliability

Reliable agentic sistemlerin ana ilkesi nedir?

  1. Mükemmel prompt’lar
  2. System design + katmanlı safeguard’lar
  3. Daha büyük modeller
  4. Daha fazla data

Doğru cevap: B

Bu sınavın özeti tek cümlede: Reliability engineered olur, prompted olmaz. Production sistem şunları üst üste koyar:

  • Doğru mimari: sequential işe tek agent, parallel işe coordinator-subagent, 4–5 tool.
  • Programmatic kapılar: tool_choice, schema, PreToolUse/PostToolUse/Stop hook.
  • Anlam katmanı: business rule, cross-reference (schema yetmez).
  • Bounded retry (2–3, specific feedback) + insan escalation.
  • Structured error (silent failure yok) + observability.
  • Context: chunking (lost in the middle), fork_session (what-if).

Prompt faydalıdır. Güçlü model faydalıdır. İkisi de tek başına production kilidi değildir.

Kilidi katman kurar. Mimari, schema, hook, retry, escalation, observability. Reliability yazılmaz. İnşa edilir.

A) Mükemmel prompt probabilistic kalır. PII, para, schema, CI parse’ı prompt ile kilitlenmez. PII ve para, ricayla kilitlenmez.

C) Daha büyük model attention, calibration, tool overload ve CI hang sorunlarını çözmez. Büyük model hang’i, overload’u ve kalibrasyonu çözmez.

D) Daha fazla data (few-shot yığını, koca CLAUDE.md) context’i şişirip lost in the middle’ı kötüleştirebilir. Şişen context, ortayı daha da kaybettirir.
